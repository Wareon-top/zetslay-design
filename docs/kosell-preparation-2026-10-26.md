# Kosell storefront preparation loading

The frontend could keep waiting on one category or preparation request; cancellation only discarded its eventual response. Repeated unchanged preparation revisions also had no stopping condition. This repair bounds each preparation read to 90 seconds, interrupts pending waits on cancellation or account changes, and pauses a batch on shared provider failures. Existing fields and selected games remain available for retry.

A failed preparation exposes “Проверить сохранённый прогресс”. It reads the existing plugin status with GET and validates the store and preparation before showing its saved revision or ready plan. It does not start another preparation. Three consecutive unchanged preparing revisions stop the loop with a resumable state. Busy/rate-limit retries remain bounded; offer confirmation never uses these retries.

Validation covers ignored abort signals, cancellation, stalled steps, repeated revisions, lost start acknowledgements, foreign or stale recovery results, and provider outages. The browser check drives the actual module against synthetic HTTP responses: failed category read, retry of missing fields, stalled preparation step, and recovery of the ready plan. No customer credentials, provider purchases or FunPay lot creation are used. A live authenticated provider failure has not been reproduced here; deployment and the original account's result still need confirmation.

`deploy/update-kosell-preparation.sh` replaces only `app/kosell-storefront.js` and its cache query in the installed `app/index.html`. It accepts exact known source identities, validates the target and script order, verifies a private backup, checks concurrent changes, and restores both files if publication fails. Tests exercise successful installation, idempotence, preflight, unknown-source refusal, corrupt backups and partial-publication rollback. Other installed HTML bytes, authentication, API containers, video/proxy banners and site data are preserved.
