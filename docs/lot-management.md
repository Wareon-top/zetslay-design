# Ручное управление обычными лотами

Встроенный редактор «Лоты и товары» меняет RU/EN названия, описания и сообщения после оплаты, цену, ручной остаток и галочку активности. Параметры категории, изображения, способ автовыдачи и секретный товар сохраняются из свежей формы и не выдаются в DTO редактора. Для автоматической выдачи остаток нельзя переписать числом. Категорию, изображения и содержимое склада владелец пока меняет на FunPay; валютные Chips не входят в этот редактор.

Каждое действие относится к одному числовому lotId/nodeId магазина владельца. Чтение сверяет пользователя страницы, собственную категорию и собственную trade-строку. Изменение требует активного тарифа/пробного периода, Bearer-сессии и свежего step-up при включённой 2FA. Подключение и доступ перепроверяются перед POST. Общий ConnectionActivity сериализует операцию с синхронизацией и штатными исполнителями. Сам read-only коннектор не получает права записи.

API:
- GET `/api/v1/funpay/lots/:id?storeId=…&nodeId=…` — свежий редактор и receipt на 10 минут.
- POST `/api/v1/funpay/lots/:id/edit` — operationId/storeId/nodeId/changes, только разрешённые изменённые поля.
- POST `/api/v1/funpay/lots/:id/delete` — те же ID и confirmed:true, отдельное подтверждение в интерфейсе.
- GET `/api/v1/funpay/lot-operations?storeId=…` — до 20 последних операций данного кабинета.
- POST `/api/v1/funpay/lot-operations/:id/check` с `{}` — только повторное чтение FunPay.

Receipt хранит пользователя, кабинет, магазин, лот, категорию, ревизию подключения и fingerprints. Исходные поля редактора и изменения пользователя в таблицу не записываются. Atomic claim защищает одну операцию от повторного выполнения и блокирует новую для того же лота при running/sending/unknown. Sending + ожидаемый fingerprint фиксируются отдельным коммитом до отправки. Потерянный ответ не вызывает повторный POST. Разрешены только собственные GET и `/lots/offerSave`, с точным заранее подготовленным body; создание лотов запрещено.

Результат изменения проверяется чтением полной формы, включая поля, которые должны сохраниться. Для удаления проверяется отсутствие ID в распознанном авторизованном списке trade; удаление последнего лота не требует оставшегося блока категории в публичном профиле. HTTP 200 сам по себе успехом не считается. При неоднозначном результате receipt остаётся unknown/sending, в том числе после перезапуска. Проверка результата ничего не пишет на площадку. Если пользователь или плагин затем изменил поля и они уже не совпадают с ожидаемым состоянием, автоматическая сверка остаётся неизвестной; повторная запись блокируется. Понадобится ручной разбор вместо слепого повтора.

Подготовка, оборванная до sending, может завершаться failed после 120 секунд; запоздалая попытка sending использует CAS и не получает разрешение на запись. Сам транспорт ограничен 75 секундами, очередь подключения — 10, браузер — 95. Отмена/закрытие формы после отправки не означает отмену запроса площадки. История операций доступна после повторного открытия раздела.

Формат удаления сверён с первичным кодом клиента FunPayCardinal: [account.py](https://github.com/sidor0912/FunPayCardinal/blob/main/FunPayAPI/account.py), `delete_lot` использует csrf_token/offer_id/deleted=1. Это исходник стороннего клиента, не официальный API FunPay. Реальные аккаунты/секреты/лоты из рабочей базы при разработке не использовались. Контракт проверен моделируемым HTTP транспортом; живую операцию на своём тестовом лоте выполняет владелец после установки. Никакие автоматические удаления или массовые операции в эту задачу не добавлены.

Развёртывание: `deploy/update-lot-management.sh` применяет миграцию `20261013_lot_management.sql`, проверяет весь suite в изолированном plugin-audit target (Node22, без сети и production env/volumes), сохраняет tests.tap и прежний образ для отката. Frontend `deploy/update-lot-management-ui.sh` меняет только две функции lots.js, HTML подключения ресурсов и новый модуль; существующие app.js, cookies входа, юридические страницы и оформления не заменяются.
