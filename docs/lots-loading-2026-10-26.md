# Inventory loading repair — 26 October 2026

User report: the Lots and Products view is empty or remains loading. The actual user's supplier responses have not been inspected. Code review reproduced two independent weaknesses: default 35-second browser reads can expire before the existing 30-second queue plus serial transport reads finish, and no initial rows are displayed until every category succeeds. There was no whole-operation deadline or cancellation.

The reader now supplies its own abort signal with a 90-second per-read deadline and a three-minute operation deadline. Only the explicit `SYNC_BUSY` contention result is retried, at most twice with bounded backoff; all requests remain GET. Cancellation, logout and store/session changes terminate the UI wait even when an underlying promise ignores abort, and late responses cannot publish data.

On the first load, successful categories appear progressively. Incomplete results are labelled as partial; summary totals remain unknown until completion. A previous complete inventory remains visible throughout a subsequent update and is preserved on any partial failure. Unknown formats, foreign store/category IDs, duplicates, invalid timestamps and source limits remain rejected. No marketplace changes, paid actions or mutations were added. Currency-specific FunPay tables remain outside the existing ordinary-lot reader.

`deploy/update-lots-loading.sh` updates only `app/lots.js` and the single versioned include in the installed `app/index.html`. It checks reviewed source and target hashes, rejects ambiguous layouts, verifies a private backup before publication, checks concurrent file changes and restores exact prior files after a partial publish failure. Existing authentication/passkeys, banners, legal/operator HTML and unrelated application files are preserved. No API switch or dependency install is needed.

Validation includes inventory/editor/raise regressions, stalled promises ignoring abort, aggregate deadlines, progressive rows, bounded contention retries, cancellation and logout races. Installer tests verify preservation/idempotency, unknown sources, tampering, no-write preflight, corrupt-backup refusal and mid-publish rollback. The Chromium DOM check uses a synthetic API and confirms progressive rows, filtering, cancellation, timeouts, retained previous rows and mobile overflow. This does not claim a successful authenticated live read of the user's FunPay account. If the repaired view reports an API/provider error, that displayed result is needed to diagnose that remaining server-specific cause.
