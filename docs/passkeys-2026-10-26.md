# Device confirmation in account security — 26 October 2026

The profile offers a prominent “Подключить отпечаток / Face ID” action. The browser/OS chooses fingerprint, face verification, Windows Hello/device PIN or a compatible phone. The site receives a credential response, not biometric data. Initial enrollment may require signing out and signing in to the same account once; there is no manual setup secret or authenticator app requirement.

After connecting, save recovery codes, then choose “Подтвердить отпечатком / Face ID” for a fresh five-minute administrative proof. The email/Telegram login challenge offers the same device confirmation. Existing authenticator/recovery-code flows remain supported. A user may add another device or remove a credential after a fresh proof; the last recovery-capable factor cannot be removed.

Binary fields are encoded/decoded for the standard navigator.credentials APIs. No external scripts, analytics or browser fingerprint collection are added. Browser prompts are bounded and abort on logout; stale results cannot bind to another account. Losing the final POST response directs the user to refresh state before trying again; acknowledged recovery codes survive a failed refresh.

The dedicated stylesheet is scoped to the account passkey panel and login dialog, with wrapping controls for narrow screens. The deploy stager inserts one versioned CSS include and replaces the reviewed security module; installed private HTML, banners and unrelated application source are preserved. SHA checks, verified private backup and rollback cover the new stylesheet too. The public security section now mentions passkeys and the continued alternative of authenticator codes.

The installer pairs this frontend revision with the pinned API revision. It does not enroll a real device or change customer secrets. The account holder must approve the native device prompt after installation.

Tests: existing security/auth regressions plus credential byte conversion, enrollment sequencing, cancellation, logout/account races, recovery retention and feature-detection copy. `scripts/check-passkey-browser.mjs` uses a Chromium virtual authenticator and a synthetic API, never real accounts, to check actual browser ceremony wiring, login dialog and mobile overflow. Physical Windows Hello/Face ID prompts require an actual device and are not claimed as tested by that automation.

## Safari compatibility follow-up

A user reported `NotAllowedError` while enrolling directly in Safari on iPhone. That error alone does not identify whether the native prompt was cancelled, platform prerequisites were absent, or browser activation was lost. The installed API also returns an empty optional display name by default, a documented interoperability issue in some browser scenarios.

The client now fills an empty registration `user.displayName` from the nonempty account name, preserving user handle, challenge, RP and mandatory user verification. If browser user activation is no longer active (or cannot be inspected), a small dialog asks for an explicit native click and invokes navigator.credentials synchronously in that listener. The same fallback works for enrollment, step-up and login. Abort/logout/timeout still close the dialog and cannot submit a stale credential. Initial enrollment errors no longer suggest using recovery codes before any exist.

Deployment is UI-only through `deploy/update-trust-ui.sh`, with the existing reviewed-source checks and verified private backup. The installed API does not need to change. The compatibility stager bumps the security module include version. Unit regressions cover empty/nonempty display names, delayed activation and contextual errors. The virtual-authenticator browser check forces the fresh-click path for all three ceremonies with an empty display name in its synthetic server options. This remains a virtual browser test, not a physical iPhone test; iCloud Passwords/Keychain, device screen lock and browser/OS support must be configured on the actual phone.

References: https://simplewebauthn.dev/docs/advanced/browser-quirks and https://simplewebauthn.dev/docs/packages/browser#troubleshooting.
